# Journal Contract — v1

## 1. Назначение

`journal/` — cold storage значимой истории кампании. Journal отвечает на
вопрос: **что важного произошло раньше?**

Journal не является источником текущих HP, ресурсов, местоположения, отношений,
квестового progress или других текущих значений. При конфликте всегда побеждает
`SAVE.md`.

## 2. Когда создаётся checkpoint

Создавай checkpoint после:

- завершения значимой сцены;
- окончания боя;
- long rest;
- major discovery;
- существенного изменения квеста;
- завершения крупного эпизода;
- окончания игрового чата, если произошли значимые события;
- явной просьбы игрока.

Не создавай checkpoint после каждого хода, броска или небольшого изменения
state.

## 3. Имена и порядок

- Имя файла — следующий свободный четырёхзначный номер: `0001.md`, `0002.md`,
  `0003.md` и так далее.
- Перед созданием проверь существующие имена непосредственно на диске.
- Никогда не перезаписывай существующий checkpoint новым.
- Номер отражает порядок создания, а не внутриигровую дату.

## 4. Обязательный формат

```markdown
# Checkpoint 0001 — Короткое название

## Metadata

- Created at: <ISO 8601 с часовым поясом>
- Campaign time: <период или момент в мире>
- Save revision at checkpoint: <revision до обновления Last checkpoint>
- Previous checkpoint: <имя файла или none>

## Player-Known Summary

<Краткий recap без спойлеров>

## Events

- <Произошедшие значимые события в хронологическом порядке>

## Character Consequences

- <Полученные травмы, ресурсы, предметы, связи или иные последствия>

## Quest and World Changes

- <Что изменилось в квестах и мире>

## NPC Changes

- <Значимые действия, состояния и изменения отношений NPC>

## DM-Private History

- <Скрытые уже произошедшие события или none>

## Historical Open Threads

- <Что на момент checkpoint оставалось нерешённым>
```

## 5. Правила содержания

Записывай:

- значимые уже произошедшие события;
- решения игрока и их последствия;
- открытия персонажа;
- появление, исчезновение или смерть важных NPC;
- изменения квестов и мира;
- долговременные последствия для персонажа;
- скрытые события, которые действительно произошли за сценой.

Не записывай:

- пошаговый transcript;
- каждый бросок, атаку и единицу урона;
- художественный пересказ ради объёма;
- текущие числовые значения как альтернативный snapshot;
- неслучившиеся DM plans в разделе событий;
- внутренние рассуждения модели или chain-of-thought.

`Player-Known Summary` и все открытые разделы должны содержать только сведения,
известные персонажу. Скрытое уже произошедшее событие помещается в
`DM-Private History`. Локальный файл не является технически защищённым от
владельца папки.

## 6. Связь с SAVE.md

Порядок checkpoint:

1. Заверши все state writes события и проверь `SAVE.md`.
2. Запомни текущий `Save revision` и `Last checkpoint`.
3. Создай следующий journal-файл и перечитай его.
4. Обнови в `SAVE.md` поле `Last checkpoint` созданным именем, увеличь
   `Save revision` на `1` и обнови `Updated at`.
5. Перечитай `SAVE.md` и проверь ссылку.

Если journal-файл создан, но pointer в `SAVE.md` обновить не удалось, сообщи о
частично завершённом checkpoint и сначала восстанови согласованность.

Checkpoint фиксирует историю на указанной revision. Текущие значения после
него всё равно читаются только из `SAVE.md`.

## 7. Исправления

Не переписывай старый checkpoint так, будто ошибки не существовало. Для
небольшой фактической ошибки добавь в конец:

```markdown
## Correction

- Corrected at: <ISO 8601>
- Replaces: <неточная формулировка>
- Correct statement: <исправленный исторический факт>
- Reason: <краткая причина>
```

Если исправление существенно меняет понимание нескольких checkpoint'ов, создай
новый checkpoint с явной коррекцией. Исправление истории не меняет текущий
state автоматически; при необходимости отдельно исправь `SAVE.md` по recovery
protocol.

## 8. Чтение journal

Не читай journal при обычном startup. Читай только:

- для `/recap`;
- по вопросу о прошлом событии;
- когда `Current Scene` явно ссылается на старый факт;
- при диагностике повреждённого state.

Сначала выбери минимально релевантные checkpoint'ы. Не загружай всю историю без
необходимости. Не раскрывай `DM-Private History` в recap, пока персонаж не
получил эту информацию в игре.

## 9. Условие корректности

Checkpoint корректен, если:

- имя уникально и следует последовательности;
- metadata заполнены;
- recap не содержит DM-only спойлеров;
- события уже произошли, а планы не выданы за факты;
- текущий snapshot не дублируется;
- `SAVE.md` указывает на файл через `Last checkpoint` после успешной записи.
